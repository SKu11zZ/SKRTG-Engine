# Character Profile authoring v2

This authoring layer turns supported external character definitions into one
normalized model and then compiles a verified `.skrtgprofile` runtime package.
It does not read `.uasset` files. Unreal Engine data enters through exported
JSON.

## Two contracts, on purpose

- `skrtg.character_definition.v1` is the neutral authoring model. It can be
  inspected, repaired, diffed, and generated by an agent.
- `.skrtgprofile v1` is the committed runtime artifact. It still contains a
  verified Rest FBX, compiled UE IK Rig JSON, alignment IK Retargeter JSON,
  metadata, and an integrity inventory.

Keeping authoring input separate from the runtime artifact means a partially
known character can be represented without pretending it is safe to run.
The package now records source format, source SHA-256, importer id/version,
and declared rest-pose kind in `profile.json.authoring`.

## Registered importers

| Input | Adapter | Result |
| --- | --- | --- |
| UE IK Rig export JSON v1/v2 | `ue_ik_rig_json.v1` | normalized and package-ready when complete |
| SKRTG Character Definition JSON | `skrtg_character_json.v1` | validated and canonicalized |
| Strict SKRTG Character Definition XML | `skrtg_character_xml.v1` | converted to the same JSON model |
| Rest-pose FBX | `rest_fbx_probe.v1` | skeleton/rest transforms only; mapping remains a draft |

“Any file” means a file handled by a registered adapter, not arbitrary bytes
or arbitrary XML semantics. Unknown schemas fail with a supported-adapter
list. New importers should convert into the neutral model and reuse the same
semantic validator and packer.

## Coordinate and pose contract

The normalized model is always:

- left-handed;
- `+X` forward, `+Y` right, `+Z` up;
- centimeters;
- quaternion component order `x,y,z,w`.

The FBX adapter applies the same UE 5.8-style scene-axis and unit conversion
used by the current exact FBX path, followed by the declared Y reflection into
the runtime convention. JSON and XML importers currently require data already
expressed in the normalized convention; they never silently reinterpret axes.

`restPoseKind` is explicit: `t_pose`, `a_pose`, `custom`, or `unknown`. SKRTG
does not infer T-pose versus A-pose from a screenshot or shoulder angle. Pose
alignment remains explicit retarget data, which is especially important for
T-pose Mixamo/SMPL characters and A-pose MetaHuman characters.

## Runtime completeness

A definition can be inspected and normalized when it has a valid skeleton.
It can only be compiled into `.skrtgprofile` when all of these exist:

1. a non-empty, topologically ordered bone inventory with local transforms;
2. an explicit retarget root that names a bone;
3. an explicit pelvis bone that names a bone;
4. one or more valid, connected retarget chains;
5. a rig asset name;
6. a Rest FBX;
7. an alignment IK Retargeter JSON whose target rig matches that rig name.

The first five appear in `runtimeDefinitionComplete` and
`missingRequirements`. The package step validates the last two and commits
nothing on failure.

## Neutral JSON shape

The authoritative schema is
[`schemas/skrtg.character_definition.v1.schema.json`](../schemas/skrtg.character_definition.v1.schema.json).
A small example is in
[`examples/character-definition.example.json`](../examples/character-definition.example.json).

Bone `model` transforms are optional input. The importer deterministically
rebuilds them from local transforms and the parent order when omitted. A
missing skeleton fingerprint is generated from the canonical bone inventory
and labeled `skrtg_canonical_skeleton_v1`; an exported UE fingerprint keeps
its own provenance label.

## Strict XML shape

XML is intentionally a small data format, not a general XML execution
environment. DTDs, entities beyond the five predefined XML entities,
processing instructions after the XML declaration, mixed text, and unknown
nested structures are rejected. This keeps agent-supplied definitions
deterministic and avoids external-entity behavior.

```xml
<CharacterDefinition schema="skrtg.character_definition.v1" schemaVersion="1">
  <Character id="example_character" displayName="Example Character"
             rigAssetName="IK_Example" restPoseKind="t_pose"/>
  <Coordinate handedness="left" forwardAxis="+X" rightAxis="+Y"
              upAxis="+Z" distanceUnit="centimeter"
              quaternionComponentOrder="x,y,z,w"/>
  <Skeleton>
    <Bone index="0" parentIndex="-1" name="root"
          localTranslationCm="0,0,0" localRotation="0,0,0,1"
          localScale="1,1,1"/>
  </Skeleton>
  <Retarget rootBone="root" pelvisBone="pelvis">
    <Chain name="Root" startBone="root" endBone="pelvis" ikGoal=""/>
  </Retarget>
</CharacterDefinition>
```

See [`examples/character-definition.example.xml`](../examples/character-definition.example.xml)
for a complete two-bone example.

## Adding another importer

An importer should have one job: parse one declared source format and produce
`skrtg.character_definition.v1`. It must declare an id and version, bind the
input SHA-256, enforce parser limits, report unsupported coordinate semantics,
and never infer a runnable mapping from names alone. Once normalized, it gets
Profile packaging, provenance, CLI JSON, and agent diagnostics for free.
